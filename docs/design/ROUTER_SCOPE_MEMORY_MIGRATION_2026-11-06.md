# Router 归属与记忆 v1：现有任务迁移、恢复和回退规格

日期：2026-11-06（Asia/Shanghai）。状态：操作协议设计；本轮没有运行迁移、备份在线实例、重启服务或修改数据库。

配套：[设计约束](ROUTER_SCOPE_MEMORY_V1_2026-11-06.md) · [验收用例](ROUTER_SCOPE_MEMORY_ACCEPTANCE_2026-11-06.md)。

## 1. 迁移的对象与不变项

迁移增加管理归属与记忆边界，不重新受理已经接受的工作。当前 Store 的 SQLite `user_version=5`；拟定新格式为 `user_version=6`、Router/Memory 数据协议 v1。实际实施前必须重新检查基线；若已有别的 schema 迁移，重新分配版本并更新规格，禁止覆盖。

必须保持：ticketId、原 Mandate 内容/强度/规则依据、原发送者身份、Assignment 顺序、Worker profile/后端/模型/参数、nativeThreadId、执行目录、输入及读取回执、停止/接管状态、外部效果和消息幂等键。新增归属元数据不能成为放宽这些约束的理由。

旧程序会拒绝更高 schema，这是必要保护。不能只向通用 records 表加入新对象而仍保留 schema 5，允许旧程序误处理新状态。

## 2. 三种操作要分别记录

| 类型 | 发生什么 | 不发生什么 |
| --- | --- | --- |
| 格式迁移 | 为旧记录补充可证明的管理归属、来源边界及兼容别名 | 不改变模型/任务目标，不共享历史，不执行任务 |
| 入口改绑 | 从生效点起把该入口的新工作交给新 Router | 不自动转交既有任务或搬迁记忆 |
| 任务转交 | 在同 tenant 内把指定任务的管理权交给另一 Router | 不改变 Mandate，不重跑已发生操作，不自动扩大结果受众 |

三者各有 operationId、输入指纹、预期版本和审计回执。不能把“把这个群交给另一个 Router”解释成以上三者全部执行。

## 3. 预览清单与归属判定

预览从一致性数据库快照读取；在线预览只用于估算，最终应用需在停写屏障下重新核对。预览包含代码/依赖/配置/数据库指纹、schema、来源身份、原生线程索引、任务/作业/出箱数量、水位及逐条处理结论；不在普通报告复制聊天全文、凭证或其他群私有标题。

每项结论只有：mapped、held、conflict、unchanged。每项列原始 ID、依据、新 owner、原受众、结果受众是否变化、执行是否在途、需要人工判断的具体原因。汇总必须满足输入数量与各分类数量相等。

| 已有证据 | 迁移判定 |
| --- | --- |
| 显式配置的来源/群 → scope 映射且唯一 | 可以 mapped；仍需核对 actor、任务与入口许可 |
| 多个旧话题明确位于同一已配置管理范围 | 共用逻辑 Router；各自历史保持隔离，不能拼接成一份模型上下文 |
| 同名群、相似任务标题、相同显示姓名 | 不能作为归属或身份依据，conflict/held |
| 完全没有新管理范围配置 | 建立只供预览的隔离旧归属建议，按旧讨论一一对应；不自动合并或正式激活 |
| 已有 worker-assignment + parentTrigger + 可重验证授权 | 保留任务和全部执行指针，新增 TaskOwnership/TaskChannel |
| 旧任务没有 Router 委派/原授权依据缺失 | held: needs_router_ownership 或 needs_authority_reconciliation；保留原记录，不重新伪造 explicit 授权 |
| 一条任务的证据指向两个管理范围 | conflict；选定唯一 owner 需要有权操作员的具体决策 |
| 跨 tenant、未知来源账号或不可确认的原生线程身份 | held；禁止自动复制或换模型重做 |

人工解决归属只改变管理元数据；不能补造原本不存在的授权。确需新授权时，以新请求建立新工作并明确关联旧结果；原任务保持原授权历史。已有任务若被人工停止，归属解决后仍保持停止。

## 4. 逐类记录映射

| 旧数据 | 迁移行为与核对点 |
| --- | --- |
| trigger / source-envelope / source-event-key / disposition / decision | 原 ID、内容指纹、身份、处理结果和去重关系不变；外置归属索引，不重放旧事件 |
| source-cursor / thread-health / 来源自己的游标 | 原样保留；首次启动不回拨游标；断档恢复要有独立范围和审计 |
| thread / subscriptions / context / correlation | 原上下文及订阅关系保留；本期不启用新的订阅直达机制；context 不变成 request/result 权限 |
| ticket / assignment / inputs / run / work | 保留原执行状态、父链、目录、实际模型及原生线程；新增 owner，不改已发生历史 |
| router-admission / router-delegation | 保留原策略版本、强度、来源与 scope；经别名解析仍按原授权核对，不用当前群绑定覆盖旧授权 |
| worker-assignment | 加 owner 映射及明确任务入口；原 discussion/source/parentTrigger 保留为追溯字段 |
| router-session / backend-thread / transcript | 原会话只保留历史索引；为新 Router 构造分受众检查点，不拼接不同话题协议历史；正常 Worker 线程继续原线程 |
| router-inbox / router-read / router-report-read | 保留消息 ID 与消费标记；旧 inbox 地址通过版本化别名解析；已读报告不再次唤醒 |
| router-result / router-reply-owner | 保留结果、触发来源及全部授权依赖；新 owner 不覆盖旧回复的受众/来源 |
| worker-command / tool-receipt / agent-input / worker-migration | 旧请求指纹和回执原样保留；别名兼容旧重试，不换哈希后再执行一次 |
| jobs | 对受影响 payload 增加新归属映射或明确 blocked 状态；保留 job ID/attempts/原错误；done 不重开 |
| outbox | 保留原消息 ID、目标、幂等键、顺序、状态；禁止迁移时产生任何外部发送 |
| settings / settings-history / prompt-use / agent-configuration | 保留历史版本；新 scope 配置单独版本化；不覆盖原模型/提示词设置 |
| approval / merge-grant / merge-attempt / review-rounds | 保留原动作与对象绑定；不能因转交继承不适用于新动作的批准；未知结果 held |
| 新记忆对象 | 仅建立可核验来源指针和任务摘要草稿；不把历史助手文本直接转成 active 事实，不向外部引擎导入全部历史 |
| 已知健康/缓存记录 | 原样保留或按注册的缓存策略重建；缓存不可恢复权威状态 |
| 未识别的持久记录/插件格式 | 预览列出；未有迁移登记与兼容证明时禁止全量激活，不能悄悄忽略 |

实现需有完整 kind 注册表，上表是必须覆盖的类别，不是允许丢弃未列条目的白名单。每个 ID 的前后映射、总数、引用完整性都要有机器可检查的报告。

旧 Worker 没有完整 context manifest 时，不能推断它没有读过其他资料。已知范围未变化且原授权可核验时，可保留原执行上下文与原受众；新增群可见性或转交到新范围前，必须补查来源/工具记录。无法证明范围的历史保持隔离，不能拿一份生成摘要当作已完成清理的证明。

## 5. 不同任务状态怎样处理

| 迁移前状态 | 准许行为 |
| --- | --- |
| queued / 尚未开始 | 迁移身份与队列，保留稳定 job/operation ID；激活并重新核对授权后才可首次执行 |
| idle / waiting / ready 但任务未终结 | 保留任务与上下文；迁移本身不唤醒。原未消费输入按原顺序处理 |
| 正在模型调用、shell 或子代理运行 | 默认等待自然到达可核对边界；不为迁移硬杀或复制执行。不能排空则推迟迁移，或由操作员明确选择中断核对路线 |
| background | 计入活跃执行；包括长命令、子代理和被豁免的评审服务，不能只看 active 数字 |
| human takeover | 保留 human 控制和 writer 归属；未明确交还不得自动调度。若后端缺少可持续验证的接管记录，整体保持 held |
| interrupted / uncertain | 原样保持待核对；确认外部效果前禁止自动重试 |
| ended ready / dropped / PR 已结束 | 保留 ended、订阅及可恢复依据；迁移不是新的恢复请求 |
| 人工 stopped | 原样停止；补归属、重新绑定或机器人消息都不能恢复 |
| outbox pending | 保留原地址；按迁移后当前许可核验，不能转发到新群“试试” |
| outbox sending / uncertain | 先核对目标端回执；无法确认则保留 uncertain，禁止自动再发 |
| outbox sent / dropped | 不重置；sent 即使进入备份恢复也不能再送一次 |

本期不承诺无停机升级。迁移默认在维护窗口完成，业务在途工作优先排空；配置允许接收事件时只能持久入箱，不产生评估、执行或外部投递。

## 6. 格式迁移状态机

| 阶段 | 必须完成 | 失败恢复位置 |
| --- | --- | --- |
| M0 inventory | 检查目标实例、路径、锁、版本及所有状态类别；生成预览 | 无运行变更，可重新预览 |
| M1 planned | 固定映射、冲突处理、应用范围、快照指纹、回退包位置 | 任何状态漂移使计划过期，不沿用旧预览 |
| M2 quiescing | 停新调度和发送，排空已开始效果，取得 writer 独占；记录平台与宿主水位 | 未排空则不能进入迁移；回到旧版时需恢复原开关而非默认开启 |
| M3 backed_up | 一致性 SQLite 备份（含 WAL 处理）、匹配代码/配置/依赖、相关原生线程导出或可验证引用、工作目录指纹、外部效果清单 | 先检验备份可读/哈希/关联关系；不合格则停止 |
| M4 staged | 在副本进行 schema 和映射变换、引用/回执/权限校验；禁网络副作用和真实模型 | 保留失败副本与错误，不修改原数据 |
| M5 switched_paused | 在独占停写条件下切换到已验证的新库/匹配程序；激活清单与 schema 一致 | 崩溃重启保持 paused，不依据某个单独文件猜测已激活 |
| M6 verified | 只读核对数量、身份、原生线程可见性和任务/出箱状态；按撤回账本检查上下文 | 不通过继续 paused；不运行任务来“验证有没有成功” |
| M7 active | 对 mapped/unchanged 且通过许可核对的工作开放处理；held 项继续阻挡 | 记录新版本开始后的副作用边界，之后进入业务恢复规则 |

停写屏障必须覆盖定时 tick、来源入箱、回执线程、配置保存、外部工具回调和原生执行 lease；不只是设置一个 UI paused。无法证明已取得独占时，M4/M5 不可执行。

应用使用稳定 migrationId，阶段记录及校验结果落盘。M4 前可丢弃副本重来；M5 崩溃通过激活清单和状态指纹恢复唯一活动库。文件/库切换必须具备可恢复的原子指针协议；不允许两个进程分别认领旧库和新库。

不支持回放的来源需在停机前证明停机窗口内消息可从平台历史补取；否则明确安排维护窗口并标记可能消息缺口，不能宣称零丢失。恢复读到重复消息使用原事件去重规则；补取不是重新执行已处理事件。

## 7. 同 tenant 内任务转交协议

1. 预览指定 ticket 的 owner、授权、TaskChannel、原生线程、外部效果和记忆依赖；校验源/目标管理权限，以及目标对全部必要材料、环境、后端的使用许可。不能先转交再补数据权限。
2. 把该任务置于 transfer-held，仅阻止自动调度与新副作用；等待在途工作可核对。人类接管仍由人控制。
3. 获取任务级 ownerEpoch，确认没有新的输入/配置/授权变化；过期则重做预览。
4. 一个事务写入新 owner、递增 ownerEpoch、旧新映射、未读 inbox 的管理目标及转交回执。task ID、Mandate、Worker 身份和效果幂等键不变。
5. 若旧模型上下文与新边界兼容，保留执行线程；不兼容则保持 held，走显式上下文接续，不能自动恢复含受限内容的历史。
6. 原 owner 的迟到工具调用/报告只作为可核对执行事实入账，不得改任务决策或对外发布；由当前 owner 判断与当前 Assignment 的对应关系。
7. 入口原受众不变。需要把结果发到新群，是独立 TaskChannel/共享许可修改，不随转交附赠。

重复执行同一 transfer operationId 返回原回执；不同内容重用 ID 拒绝；两个并发转交只能一个提交。跨 tenant 直接转交不进入该流程。

转交前已进入出箱的 pending 回复按原 ID 挂起，由新 owner 核对其授权/受众/事实版本后批准继续或撤销；不复制新消息来替代原消息。已有 sent 回执不受影响。转交后才到达的旧 owner 输出不能自行成为新 pending 回复。

## 8. 回退与恢复决策

| 新版本经历 | 回退策略 |
| --- | --- |
| M0–M4，没有修改活动库 | 丢弃或保留隔离副本供诊断，旧实例按原配置继续 |
| M5–M6，尚未开始新外部效果 | 停止新程序，恢复匹配旧程序/配置/备份；核对接收事件水位，不能丢弃维护窗口输入 |
| M7 后发生执行/发送/审批变化 | 不能直接覆盖旧快照；先导出增量效果、请求与回执，核对外部状态，再选择修复前进或受控旧版恢复 |
| 新版发生过撤回/清空/权限收窄 | 恢复前重放独立保存的最新撤回账本；旧程序不能表达这些约束时，禁止用旧程序恢复对外服务，只能离线读或修复前进 |
| 新版已接受新任务或改变跨群归属 | 必须证明这些新增状态可无损映射到旧版；本期不承诺通用降级转换。不能表达时保持新库并修复前进，不能只恢复旧任务丢弃新任务 |
| 原生模型线程已继续推进 | 不把旧 SQLite 与较新的原生线程假装配对；先核对线程/目录/工具效果，无法证明一致则保持 held |
| 外部记忆索引尚未清理或版本未知 | 先停用该提供方，用当前受权本地数据；不能恢复旧索引就开放查询 |

副作用清单需包含已发送消息的目标/消息 ID、幂等键、文件/提交或外部对象版本、批准与撤销状态、不确定项。恢复不能撤销已经发送到群里的内容，也不能把未核对的发送当作失败重发。

最新撤回账本须在回退覆盖范围之外保留其完整性校验副本，并记录恢复所需最小序号。缺少最新账本或效果增量时，不满足在线恢复条件。清理备份前先证明对应恢复窗口已关闭，不能靠旧备份绕过删除语义。

## 9. 当前实例的设计性结论

“搞大事情”的独立部署与旧 AgentHub 实例使用不同状态目录。本方案不合并这些数据库，也不因为共用飞书机器人就认为属于同一管理范围。实施前应分别只读盘点，由明确的实例/来源映射决定迁移对象。

现有 schema 5 数据先走格式迁移；若其中没有任务，仍要验证来源游标、出箱、准入和设置，不以“active=0”推断没有需要迁移的数据。已有任务必须按本文件分类，不能统一重新提交给新 Router。

## 10. 交付证据

每次演练输出：版本与快照指纹、前后分类/引用计数、不可变字段对照、唯一 owner 检查、去重/回执对照、原生线程可用性、撤回账本水位、逐阶段故障注入结果、回退后的外部回读结果。

任何 held/conflict 项仍需展示；只有计划内全部项目得到确定处理，且相关验收均通过，才能把本次迁移标为 complete。完成归属映射不等于任务执行完成。
