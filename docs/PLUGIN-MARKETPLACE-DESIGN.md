# Roppo 插件市场方案

状态：2026-11-09 已批准的设计提案。实现与发布边界见 [使用说明](PLUGIN-MARKETPLACE.md) 和 [验收记录](PLUGIN-MARKETPLACE-ACCEPTANCE.md)。

## 定位与现状

让用户在 Roppo 内发现、安装、配置、更新和停用插件，无须使用终端。市场是宿主内置的管理页面；Agent 看板等功能继续作为独立插件。

本地已有 source v2、workspace-view v1 两种包，已有 pack、inspect、stage、摘要校验及不可变对象目录。当前 CLI 的 stage 只安装文件并生成新配置，不会自动激活。现有设置覆盖层也不持久化市场安装记录，需要新增管理生命周期。

本次通过 GitHub 连接器读取 `pythc/agent-hub/main/plugins`，列表仅含 `codex`。该目录的插件面向外部客户端，不能直接视作 Roppo source/workspace-view 插件。新看板及本地应用连接器要先完成发布，市场才有真实可安装条目。

首版承载应用连接器和工作区页面。模型后端、工具包和角色模板须有对应已验证的运行契约后再加入。目录中没有匹配 manifest/发行包的普通文件夹不会出现“安装”。

## 页面设计

沿用现有黑白主题、字体、可折叠导航与账号。复用“工具与应用”入口，页面标题为“插件与工具”，不增加常驻侧栏项目。

```text
插件与工具                         管理来源   从 GitHub 添加

市场       已安装       更新 ②       工具连接
──────────────────────────────────────────────────────────
搜索插件…                      全部 / 应用连接 / 工作区页面

 [图标] Agent board                [图标] Slack
  团队状态、任务与辅助决策用量       在群聊中接收任务并报告进展
  pythc · 工作区页面                pythc · 应用连接
                           安装                         安装

 [图标] Linear                     [图标] Feishu
  同步事项与任务进展                 连接飞书群聊
  pythc · 应用连接                  pythc · 应用连接
                           安装                         安装
```

以上为布局示意；条目、版本和安装状态均由真实目录与安装记录提供。

- 市场：搜索和类型筛选；卡片只显示名称、图标、一句用途、维护者、类型和主操作。暂不加入评分、下载排名或没有数据依据的推荐。
- 已安装：使用紧凑列表，显示当前版本、运行状态及连接数量。支持打开、配置、禁用、卸载。
- 更新：显示当前版本 → 可用兼容版本、更新说明、权限变化及受影响连接。支持检查更新、忽略该版本；每项仍有独立执行结果。
- 工具连接：保留现有 MCP/工具连接功能及旧链接行为。
- 管理来源：管理内置 GitHub 目录和用户添加的目录，显示最后同步时间、失败原因、缓存状态。刷新失败不清空已安装列表。

点击条目打开右侧详情抽屉，保留列表位置、筛选和滚动位置。抽屉提供介绍/截图、版本历史、权限、仓库链接和固定底部操作按钮。摘要、commit 和 API 版本放在可展开的技术详情中。

动作示例：未安装为“安装”；连接器已下载但未配置为“配置连接”；看板已激活为“打开”；更新被主机运行状态阻挡时为“已下载，待激活”。“已安装”不等同“已连接”。

动效只表达实际状态：抽屉展开、按钮切换、真实下载进度、步骤完成。未知下载总量时使用不定进度。支持 reduced motion、键盘、移动端全屏详情和黑白主题。

建议路由为 `#integrations/market`、`#integrations/installed`、`#integrations/updates`、`#integrations/tools`。旧 `#integrations` 保持工具连接语义，导航入口指向 market。

## GitHub 目录与发行包

建议首先使用现有仓库，无须额外建设市场服务器：

```text
pythc/agent-hub
  plugins/catalog.json          可发现条目及兼容发行版本
  plugins/agent-board/          源码、manifest、README、预览图
  plugins/slack/
  plugins/linear/
  plugins/feishu/

GitHub Releases
  plugin-agent-board-v0.1.0
    agent-board-0.1.0.tgz       预先构建的安装包与许可证
```

目录负责发现、介绍和版本清单；Release 资产负责分发可运行包。客户端不需要构建工具链，也不会在安装时执行仓库里的 npm/install 脚本。高级入口接受 GitHub 仓库或子目录链接，解析为明确的目录项或已经打包的目录；只提供源码时显示“尚未发布安装包”。

目录包含：稳定插件 ID、仓库数字 ID/路径、维护者、类型、用途、许可证、图标/截图，以及各版本的宿主特性要求、插件协议、平台/运行环境、发布说明、精确 commit、Release 资产 ID、归档 SHA-256 和规范化包摘要。

已有 source v2 manifest 不必为了市场强行改变格式；市场目录把它映射为 source 类别。下载后再以实际 manifest 校验类别、ID、能力和摘要，不能只信卡片信息。

版本选择按语义化版本和实际宿主特性判断，不使用单仓库的 latest release 推断所有插件最新版。默认稳定版；预发行版需主动选择。确认安装计划后锁定目录 commit、目标版本和两个摘要，执行期间远端 main/tag 变化不能改变已选包。

推荐使用 GitHub immutable releases。它能锁定已发布资产和关联 tag；启用后按 draft → 上传资产 → 发布的顺序操作。普通 Release 也必须验证固定摘要，同一版本被替换为不同字节时拒绝静默升级。

发布 CI：验证 manifest → 类型检查/测试 → 打包 → 生成摘要/发行说明 → 发布资产 → 更新目录项。目录只有在资产可下载且通过校验后才收录新版本。

来源身份与包完整性分别记录：摘要证明字节匹配；维护者标记来源于预置/用户授权目录，不能从 star 数或任意 manifest 自称推导“可信”。同名插件来自不同仓库时禁止覆盖；迁移来源需要单独的可审阅计划。

## 安装与配置

```text
查看详情 → 生成安装计划 → 安装 → 下载 → 校验 → 安装文件
                                              ├─ 工作区页面：启用 → 打开
                                              └─ 应用连接：配置账号/群聊 → 验证 → 激活
```

用户在详情中能看到所需权限、版本兼容性和实际影响。普通安装只需一次明确操作；只有新增权限、凭据授权或主机需要重启等实际变化才追加相应步骤。GitHub 阅读凭据与 Slack/飞书等应用凭据分开管理。

包安装属于当前本机实例。一个 Slack 插件可以供多个已授权 Slack 连接使用；安装包不会自动获得任何群聊或 Router/Worker 权限。连接与工具授权继续走现有来源范围、成员和 Agent 配置逻辑。

首版公网目录可匿名读取；私有仓库支持用户主动配置的只读 GitHub 凭据。凭据仅由宿主持有，不进入市场页面持久存储、插件包或日志。网络请求采用缓存/ETag、有限重试及速率限制退避；GitHub 不可用时仍可查看本地插件。

## 更新、回退和卸载

| 类别 | 首版建议策略 |
| --- | --- |
| 只读 workspace-view v1 | 新增可持久化的局部激活能力；验证新包后切换版本、重建该插件 iframe，保持对话和运行任务 |
| source v2 | 下载与激活分开；沿用现有主机级静默条件、协议检查和受控重启，展示所有受影响连接 |
| 状态协议不兼容 | 拒绝一键更新，明确提示需要迁移，不能用旧包覆盖新状态 |

目前页面包也只有 CLI 暂存能力，局部激活是本方案待开发能力。当前 source 更新检查是主机级而非单插件级：开放任务、目标、待处理作业或未确认外部写入可能阻止更新。首版显示具体阻碍，不自动停止任务、清空队列或宣称“等一会一定成功”。

默认自动检查更新、由用户选择安装。页面包与连接器均保留前一兼容版本。回退只切换包与适用配置引用，保留账号、密钥、任务、游标和投递回执。已经发生的外部行为不能通过回退插件代码撤销。

下载或验证失败：旧版本继续运行。局部页面激活失败：恢复前一可用页面版本。连接器启动失败：依据安装事务和宿主恢复流程恢复可兼容配置；存在不确定外部行为时进入“需要处理”，不盲目重复执行。

禁用与卸载分开。禁用停止该插件的新活动/隐藏页面；已有连接或任务引用时，卸载显示依赖并阻止直接删除。默认保留连接设置、账号和任务历史；彻底清理数据是独立动作。缓存包只在无激活、回退及任务引用后回收。

## 宿主实现

新增三个职责清楚的模块：GitHub 目录/下载客户端、插件安装管理器、内置市场页面。复用现有包校验、不可变对象目录、来源进程隔离、view sandbox 和配置重建，不另写执行器。

服务端提供 catalog、installed、updates、plans、operations 等接口。读取不变更状态；安装/更新/禁用/卸载要求宿主操作员身份和同源写入验证。插件自身不能通过 sandbox bridge 安装别的插件。

安装计划记录期望的当前安装版本/配置 revision、来源身份、目标摘要、权限差异、依赖和激活方式。执行绑定计划与 request ID，同一请求重试不能重复安装或重启。并发安装/配置修改采用序列化和 revision 检查；冲突重新生成计划。

新增版本化、原子提交的托管插件覆盖层与安装事务记录：

- 将手工启动配置与市场托管引用明确区分，定义冲突处理；不能重写用户原始配置或让旧 settings 快照覆盖刚安装的版本。
- 在新进程启动时加载托管插件引用；激活状态、对象摘要、来源、上一版本及失败阶段可恢复。
- 扩展已有备份/恢复逻辑，覆盖插件引用、记录及所需对象。不能只恢复配置却丢失版本文件；也不能借插件回退恢复旧任务库。
- 协调磁盘引用与数据库提交标记，处理下载中、校验后、切换中和宿主重启时的崩溃。成功标记只在确认目标版本实际激活后写入。
- 限制归档大小/文件数/展开体积，拒绝路径穿越、软链接及非约定入口；下载重定向不转发 GitHub 凭据到资产域名。

作业状态至少包含 downloading、verifying、installed、needs-configuration、waiting-for-idle、activating、active、failed、needs-attention。页面从真实持久化状态恢复进度，不靠动画定时器模拟完成。

## 分阶段交付与验收

1. 发布基础：目录 schema、两类包验证、发布 CI、兼容性解析；先把 Agent board 和可验收连接器真正发布。
2. 市场闭环：目录/详情、已安装、安装与配置、更新检测、事务记录和页面包局部激活；实际从 GitHub 下载看板完成验收。
3. 连接器生命周期：依赖影响展示、待激活/受控重启、失败恢复、回退和卸载；验证多连接共用一个包且保留游标/回执。

验收包括：干净实例安装、重启持久化、离线缓存、GitHub 认证/限流、下载失败重试、权限扩张、旧宿主不兼容、包篡改、同名异来源、源代码目录无发行包、连续点击、并发设置修改、每个激活阶段崩溃、更新期间运行任务保护、回退后不重复投递，以及黑白主题/窄屏/键盘/真实状态动效。
