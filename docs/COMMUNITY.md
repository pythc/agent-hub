## How decisions are made

Maintainers review contributions and decide what is merged and released. Anyone may propose a change. Substantial changes should begin with a discussion of the problem, user experience, compatibility, and a way to verify the result. Record the accepted scope in an issue, then link the implementation PR.

The [roadmap](../ROADMAP.md) describes priorities without promising dates. There is no formal steering committee or guaranteed review schedule. Changes to governance should be discussed publicly before being adopted.

## Issue triage

- `bug`: observed behavior differs from the intended contract.
- `enhancement`: a concrete improvement proposal.
- `documentation`: usage, translations, or contributor documentation.
- `needs-reproduction`: more evidence is needed before implementation.
- `good first issue`: bounded work with clear steps and verification.
- `help wanted`: maintainers welcome contributions.
- `area:ui`, `area:runtime`, `area:browser`, `area:adapters`: the relevant component.

Maintainers can request a minimal reproduction, turn an open-ended issue into a discussion, or close a duplicate with a link. Keep rejected alternatives and tradeoffs discoverable rather than treating disagreement as misconduct.

Please follow the [code of conduct](../CODE_OF_CONDUCT.md). Community infrastructure is only a starting point; useful questions, respectful reviews, and shared working examples make it valuable.
