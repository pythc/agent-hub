# O09.1: operator attention, observation only

This backend slice adds `GET /entry-workspace/attention` to the existing current-operator session and same-host HTTP service. It reads existing task attention, native approvals, project acceptance reviews, workflow proposals and uncertain effect records. It adds no UI, inbox table, answer endpoint, execution permission, background work or retry. **O09 remains open**: this is not the persistent, cross-hour business DecisionRequest described in MASTER_TODO. Real IM and ACP acceptance still requires separate authorization and has not been performed.

## API and navigation contract

The GET accepts only `offset` (0–1,000,000, default 0) and `limit` (1–100, default 25). Supplied values must be single canonical decimal integers; duplicate, empty, whitespace, exponent and unknown parameters are rejected before conversion, including repeated parameters with equal values. It returns `{schema:1,readOnly:true,observedAt,total,offset,limit,more,items}`. `total` counts matters, not tasks: two independent permission requests for one task remain two matters. Existing record times sort descending, followed by stable opaque IDs; records without a creation time use null and sort last. No new priority is inferred. Pagination observes the current facts on each request; it does not promise a frozen historical snapshot.

Each item has a stable opaque `id`, allowlisted `kind` and `state`, optional existing `taskRef`, a fixed platform `sourceLabel`, actual `createdAt` / `expiresAt` or null, an `observed` fingerprint and an existing-entry `next` descriptor. Kinds are `task_question`, `native_question`, `native_approval`, `workflow_review`, `project_review`, `effect_unknown`. States are `needs_reply`, `waiting_permission`, `needs_review`, `outcome_unknown`, `expired`, `unavailable`, `stale`. The fingerprint describes observed facts and configuration/ownership revision; **it is not an action token or permission**. Navigation kinds are `task`, `records`, `workflow`, `project_review`; the IDs refer to existing pages/records. No arbitrary URL is emitted, and unverified IM links are never guessed. There is no execute/approve/send/retry action in this DTO. Any future consumer must use the existing page and its existing server-side authorization and revision checks.

The list omits question text, prompts, report bodies, native arguments, provider output, commands, session/turn/request IDs, actor IDs, recipients, account/issue labels, target URLs, filesystem paths and configuration credentials. Platform names come from fixed display labels, rather than arbitrary instance labels or provider metadata. `taskRef` and navigation IDs are existing internal references for navigation, not displayed task titles or proof of authorization. No user decision can be submitted to this read-only endpoint. Invalid queries return fixed `operator_attention_query_invalid` (400); unexpected failures return fixed `operator_attention_unavailable` (503), without underlying exception text. Non-GET methods return 405. Existing operator authentication is checked again at the endpoint, and responses remain `no-store`.

## Existing authority, currentness and read-only boundary

The complete synchronous projection runs inside both `RouterScopes.readOnly` and the O07 `RouterMemory.readOnly` guard. The scope guard is a nested in-memory depth counter with `try/finally` restoration, not a permission object or persistent state. In `route`, an existing route returns as before; a missing route throws before entry/task derivation or persistence while that explicit read scope is active. This also covers indirect scheduled/goal-wake authorization calls that resolve their original anchors through `scopes.context`. With depth zero, ordinary execution keeps its existing lazy-route behavior. The boundary is for synchronous reads only: it does not isolate arbitrary async callbacks or prevent malicious plugin side effects, and it is not a general database transaction/write interceptor. An unreconciled revocation ledger fails closed without applying it. Current source policy, source membership, task ownership, scope admission, active task channels, history cleanup and saved context are checked. Private actor entries are deliberately omitted from this first operator-wide list. Managed visibility requires an existing Router route with matching entry revision and tenant epoch; a missing route is not created on GET. Goal context uses the existing goal authority after that route guard, including its context/replanning validations. No `ExecutionTrace` instance is constructed by the projection, since its constructor can install projection hooks. The HTTP server's existing startup hook installation precedes all GET tests and is not attributed to the GET.

Questions use existing `ticket.attention.id`; no new question or deadline is manufactured. Existing task-continuation quarantine hides old questions. An ended or Router-cancelled task has no active question or permission row. A question without a current running/blocked assignment is labelled stale rather than inferred actionable. Existing unknown operations remain visible after task stop or assignment replacement when the source and context remain readable. Stops do not claim to retract external effects. Source revocation hides those records rather than granting new access.

Native approval metadata and a live native waiter are separate. The new `Approvals.hasLiveRequest(id, now)` only reads the existing pending Map and record: it never creates a waiter, expires a request, changes a timer, consumes a Promise, answers, persists or extends a deadline. Basic malformed metadata returns false. Observation time, creation time and expiry must be safe integer milliseconds in the JavaScript Date range 0–8.64e15; invalid/nonfinite or fractional values never create a valid wait or a manufactured deadline. A supported native request additionally needs a matching current running assignment, human-wait phase, native thread and turn, and an actual creation time strictly later than assignment start. Equal timestamps or missing attribution conservatively give `unavailable`. Supported native methods are the existing command, file-change and permissions approvals and native user-input request. A live native user-input request is a separate `native_question` / `needs_reply` matter, not a permission approval. `waiting_permission` describes an existing wait, not new permission to approve; the existing answer endpoint remains authoritative.

The original 120-second host native TTL and startup expiry behavior are unchanged. A persisted pending row without its original live waiter is never treated as live. Expired records can be viewed on a still-open task, with their actual deadline. `acp/permission` and unknown protocol methods remain view-only/unavailable even if a host Promise exists. ACP's envelope deadline, when valid, is capped by the stored host deadline; it is never substituted for a new authorization or extended. A missing or malformed deadline is null, not a predicted two-hour/next-day window.

Workflow proposals retain their original row ID, source/target, entry revision, owner epoch and data revision. The projection does not call `WorkflowActions.current/decide`, `workflowState` or `applyWorkflowState`. Current configured target, capability and existing entry permission are checked locally; changed proposals are stale. Pending project review requires existing goal visibility and independently read-only acceptance freshness to be `needs_review`; absent or changed evidence is stale. Neither case grants approval. Applying or uncertain workflow effects, tool/browser receipts, interrupted work, uncertain runs/jobs/outbox, and other retained uncertain effect receipts offer only the existing records/workflow view. The projection does not claim remote readback or successful delivery. Shared Router replies are visible only when every referenced task remains readable.

## Compatibility and rollback

No database format, native TTL, protocol, source authorization or existing mutation endpoint changes. The RouterScopes addition only guards missing lazy routes during an explicit synchronous observation; existing routes and default execution remain unchanged. The only Approvals addition is a pure liveness query. Startup still expires old pending native approvals. Rollback removes the projection/GET, tests and pure query without migrating or deleting task, approval, effect, review, job, audit or outbox records. There is no new durable state or journal to reconcile. Persistent business questions, qualified reply/recipient/amount contracts, cross-machine answer correlation and overnight decision recovery remain future O09 work and must not reuse the short-lived native waiter as business authorization.


Independent-review follow-up covers real `schedule.put/run` → Worker delegation, real goal-controller wake → Worker delegation, and scheduled input → dependent goal-wake → original human anchor. In each case all existing routes form a visible positive baseline; deleting only the inner anchor route makes observation fail closed with every SQLite table and live approval Map and each original waiter object unchanged, even while the immediate task/parent routes still exist. Nested normal return and throw restore the depth, and ordinary non-observation context lookup still creates the route. A separate signed in-process pair/submit fixture exercises actual independent-team delegated authority and its private route without network: its authority itself reads peer/lease facts, while missing private context is refused inside the nested guard and the operator-wide projection continues to omit that private entry. This is not a claim that private remote tasks have become operator-visible. All model/history/delivery spies remain zero. Strict Date boundaries and HTTP duplicate/blank/whitespace parameters have regression coverage.
