# 统一 Router 管理入口

本轮完成路线图第一步：在 `execution.router.mode = "host"` 时，让人类请求、准入表放行的消息和书面规则触发的事件都进入持久 Router。Worker 的委派、后续指令和结果回收由 Router 管理。此次没有实现总目标与子任务关系、正式验收/返工协议或组织身份体系。

## 实际行为

```text
来源事件 → 共同的 SourceScope / Policy.gate
             ├─ 拒绝 → 保存准入原因
             ├─ 显式授权 → 持久 Router
             └─ 推断 → 逐条书面规则评估
                        ├─ observe → 保存判断，不执行
                        ├─ 无匹配 / 无效判断 → 忽略或标记不可用
                        └─ auto + 匹配 → 持久 Router

持久 Router → worker_manage → DeepSeek Engine 的任务/委派生命周期
Worker 回执 → Router 内部收件箱 → Router 汇总 → 原来源、原话题
```

规则评估是只读的临时模型调用，使用 Router 的后端与参数；它不能管理 Worker。推断事件因此比显式请求多一次准入评估调用，持久管理会话仍只有一个。未提供回复渠道的事件可以进入管理流程，结果保存在宿主中。

| 输入 / 状态 | 行为 |
| --- | --- |
| 已列入允许名单的人明确寻址 | 按显式授权进入 Router，`off` 不禁止此类请求 |
| 未列入名单，但准入表为 `explicit` | 同样进入 Router，不再被第二套 allowedActors 判断拒绝 |
| 合法会话中的未寻址后续消息 | 通过同一 gate 判断；会话依据仍须有效，仅有旧 session ID 不构成授权 |
| 机器人 / 推断消息 | 必须通过来源范围、机器人名单或准入表、模式和书面规则检查 |
| observe 中建议新建或附加任务 | 只记录判断，均不会启动/唤醒 Worker |
| 已有任务的机器人更新 | 获准后由 Router 发送内部指令；原始外部消息不直接投递给 Worker |
| 机器人要求停止或重新开启已结束任务 | 不允许；推断事件也不能修改 Worker 配置 |
| 重复事件 | 返回 duplicate，不重复评估、委派或发送 |

Router 的准入记录与 Worker 的任务 accept Decision 是不同对象：进入管理会话不等于已经创建或完成任务。`router-admission` 保存原始事件、授权强度、来源依据、策略版本、逐条规则判断和状态。实际 Worker 任务仍由原有 Engine 创建，继承原有显式/推断强度和匹配规则；没有把机器人伪装成人类，也没有把推断授权提升成显式授权。vendored DeepSeek core 未修改。

## 授权与持久化

- 复用 `makeScope`、`makePolicy` 和共同的逐条规则校验；准入表、监听范围、off/observe/auto 的定义不另写一套。
- 准入记录、排队和委派回执与对应状态在同一个 SQLite 事务中落盘。规则在评估期间变化时，旧结果作废并重新评估；策略改动后又恢复原值，也不会因旧 job ID 而漏掉工作。
- Router 开始运行、管理工具调用、Worker 调度/受管工具调用、汇总完成及实际发送前都会重新核对授权。已经发生的外部操作不可能靠撤回授权逆转；不确定交付仍保留原记录，不自动重发。
- 回复保存其授权来源，包括通过 inspect/result 读取的任务回执；原消息的监听范围、话题和消息引用随回复保留。
- 普通输入不直接扇出到 Worker，即使旧 Worker 订阅了相同外部话题。操作员显式接管、维护接口和 client 模式仍是独立的控制入口，不被冒充为普通用户会话。

宿主状态增加 `routerAdmissions` 和 `routerMigrations`；判断失败可以从准入原因及任务错误查到。本轮没有新增 UI 页面。

## 升级与回退

1. 停止接收新工作并核对在途执行/不确定交付，保存匹配的程序、启动配置和完整状态备份。
2. 新版读取旧 Router 委派时，只恢复按当前策略仍属显式授权的来源，且不额外重跑旧 Router 回合。缺少可证明授权的旧会话需要新的明确请求。
3. 旧 Engine 尚未接受的评估转入统一准入。已接受但没有 Router 归属的旧任务及其待发送消息保留并标记 `needs_router_ownership`，不会直接派给 Worker。先检查原任务及外部结果，再停止旧任务、向 Router 发起新的明确请求，避免重复副作用。
4. 回退必须恢复匹配的旧程序、配置和升级前状态，并核对升级后已发生的外部操作。此轮未提高 SQLite schema 号，但旧程序不理解新增准入 job/record，因此不能仅换旧源码继续运行新状态。

此次用隔离状态验证了恢复与兼容分支；没有执行运行实例部署或旧版本二进制回退演练。
